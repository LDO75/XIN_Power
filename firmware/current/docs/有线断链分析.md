# 6.2.2有线断链分析

## 日志证据

用户提供19:26起日志，在19:28:21报告ClearCommError failed / PermissionError(13,拒绝访问,Windows错误5)，19:28:42报告GetOverlappedResult failed / 同类错误。19:28:27与19:28:57再次打开COM9均收到6.2.1 INFO。

这些错误来自Windows串口API调用失败；pySerial以异常形式报告。不是固件返回的FAULT、CRC错误或ACK超时。日志不足以判断设备是否复位、USB瞬断、串口驱动异常或电气干扰，也不能凭输出OFF推定MCU复位。
依据：[pySerial Windows实现](https://github.com/pyserial/pyserial/blob/master/serial/serialwin32.py)、[Microsoft ClearCommError](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-clearcommerror)。

## 本版修正

二进制调度原来写死20ms，RATE不生效。本版按各通道周期调度，默认40ms；87字节一帧，25Hz=2175字节/秒，占115200 8N1约19%，50Hz约38%。原50Hz理论上也未超过线路带宽，不能把Windows“拒绝访问”简单归因为回传太快。

上位机保持后台接收/DMA固件，系统读写错误保留完整原因并尝试恢复原有线端口5次，1.8秒间隔。重新握手配置40ms并读取STATUS，不自动恢复输出，不重发旧的调压或校准保存。扫描不会替换恢复端口，手动操作可取消。蓝牙不自动切换进入此有线恢复流程。

普通命令最终确认超时独立处理，继续接收并报告操作结果未知。当前命令同序号重试仍用于应对丢包，最终超时之后结束该命令；应通过读取状态确认。

## 实测判断

日志的中文状态摘要限5次/秒，完整数据在后台记录；不能根据摘要条数认定回传5Hz。实测查看回传速率和CSV/JSONL中的全部遥测。
若新版仍触发Windows错误，请保留断链前后日志；结合Windows设备是否消失重现、USB驱动/线缆、供电与高电流切换条件进一步定位。本版改善恢复和诊断，没有实机证据证明根因消失。
